# Dify 1.17.1 基线升级方案

## 一、升级背景与目标

当前平台已经在 Dify 原有能力上完成账号与工作空间治理、托管执行引擎、Console 调试、KMS/S3 存储安全以及健康监控等企业级增强。随着官方基线升级到 1.17.1，应用执行、账号服务、数据库会话、文件存储和前端运行状态等内部职责都发生了变化，旧版企业改造不能直接整体搬入新版本。

本次升级的目标不是“把旧代码重新合进去”，而是以 Dify 1.17.1 为新的长期基线，在保留现有企业能力和历史数据的前提下，把这些能力重新接到新版原生职责上。

| 目标 | 说明 |
| --- | --- |
| 升级官方基线 | 平台基线升级到 Dify 1.17.1，后续功能继续基于新版演进 |
| 保留企业能力 | SkyOA、工作空间治理、托管执行、KMS/S3、健康审计等能力继续保留 |
| 避免旧架构包袱 | 新版已有职责直接复用，接口变化较大的部分按 1.17.1 重新接入，不长期维护旧兼容层 |
| 保留历史数据 | 账号、工作空间、执行任务、文件引用、租户私钥等已有数据不因升级丢失 |
| 支持可控发布 | 升级先在隔离环境完成迁移与回归，再进行版本切换，并保留明确回滚点 |

---

## 二、现有能力与升级范围

现有企业能力按五个方向整理。升级方案只描述这些能力在新基线中的保留方式，不展开到具体文件和提交。

| 能力方向 | 当前能力 | 升级处理 |
| --- | --- | --- |
| 平台基座与租户治理 | SkyOA 登录、超级管理员初始化、邀请注册、默认工作空间、工作空间管理与权限 | 保留业务规则，按 1.17.1 账号、会话和权限职责重新接入 |
| 托管执行引擎 | 统一准入、执行策略、队列、Scheduler、双 Worker、容量管理、任务管理、Streaming/Blocking | 保留调度体系，执行部分接入新版原生 Runtime |
| 应用执行与 Console 调试 | Workflow、Chatflow、Chat、Completion、Agent、单节点、迭代、循环、Human Input、定时触发 | 以新版各应用 Generator 和调试能力为执行主体，托管引擎负责准入和调度 |
| 存储与数据安全 | KMS 凭据、S3、文件 Key、租户私钥、缓存隔离 | 保留企业安全策略，复用 1.17.1 原生 S3 与文件能力 |
| 管理与可观测 | 系统管理端、Worker 健康、OTel、审计、部署脚本与环境配置 | 随新版运行方式适配，保持管理和观测能力 |

当前迁移分支已经完成平台构建与部署支持的代码迁入，其余功能已经形成迁移设计，后续按本方案分阶段实施。构建完成不等于升级完成，最终仍以完整运行、数据迁移和业务链路验收为准。

## 三、升级总体方案

### 3.1 升级原则

| 原则 | 方案 |
| --- | --- |
| 以新版为主 | 1.17.1 已有的执行、账号、文件和权限职责直接复用，不用旧实现覆盖新版 |
| 保留业务能力 | 企业自定义的调度、身份治理、KMS、安全和管理规则继续保留 |
| 业务与底层解耦 | 保留“做什么”的业务规则，变化较大的“怎么执行”按新版接口重接 |
| 数据优先兼容 | 不通过删库、重建账号、重建私钥或批量重命名对象来解决升级问题 |
| 分阶段启用 | 能独立验证的能力先迁，执行引擎和应用入口在公共底座稳定后再启用 |
| 可观测后放量 | Scheduler、Worker 和核心链路具备健康检查后再进入正式切换 |

### 3.2 目标架构

![Dify 1.17.1 基线升级目标架构](assets/dify-baseline-upgrade/dify-baseline-upgrade-architecture.svg)

升级后的职责分工保持简单：

- **Dify 1.17.1** 负责官方应用运行时、Console/WebApp、原生权限、文件和基础执行能力。
- **企业增强层** 负责统一身份、租户治理、托管调度、安全存储和平台管理。
- **PostgreSQL、Redis、S3、KMS 等基础设施**继续承载现有数据，不因为应用基线升级重新建设。

### 3.3 迁移方式

| 迁移方式 | 适用内容 | 处理方式 |
| --- | --- | --- |
| 直接保留 | 与新版职责基本独立的企业业务规则 | 保留能力和数据结构，只调整必要接口 |
| 适配迁移 | 能力不变，但新版 Session、权限或调用接口变化 | 按 1.17.1 接口重新接线 |
| 基于新版重写 | 旧实现深度依赖旧 Runtime 或旧 Generator | 保留业务目标，在新版原生能力上重新实现 |
| 暂缓启用 | 外部协议、历史数据或新版能力边界尚未确认 | 不强行兼容，确认前保持官方路径或不启用 |

## 四、核心功能迁移方案

### 4.1 平台基座与租户治理

这一部分保留公司已经形成的账号和工作空间规则，但登录、注册、会话和权限判断都以 1.17.1 的账号服务为基础。

| 功能 | 保留内容 | 升级方式 |
| --- | --- | --- |
| SkyOA 登录 | 统一身份、open_id 映射、自动注册规则、登录态 | 保留 SkyOA 协议，按新版账号与身份关联接口重接 |
| 超级管理员初始化 | 首次初始化、唯一管理员、失败保护 | 接入新版初始化流程，不恢复旧的大范围清理逻辑 |
| 邀请注册 | 邀请、过期、撤销、重复接受、成员角色 | 接入新版激活和成员管理能力 |
| 默认工作空间 | 自动加入、唯一默认空间、owner 保护 | 保留公司规则，使用新版成员与当前空间状态 |
| 工作空间管理 | 创建、指定 owner、归档、权限控制 | 复用新版工作空间查询与成员状态，保留系统管理员能力 |

核心目标是：**账号和工作空间业务规则不变，但不再依赖旧版隐式会话和旧控制器结构。**

### 4.2 托管执行引擎

托管执行引擎继续作为企业平台的执行调度中心。升级重点不是重新设计调度体系，而是让 Scheduler 和 Worker 调用 1.17.1 的原生应用执行能力。

| 模块 | 升级方案 |
| --- | --- |
| Policy | 保留 critical / standard、优先级和版本控制 |
| Admission / Queue | 保留统一准入、全局与租户队列、幂等和输入快照 |
| Scheduler | 保留独立 Scheduler、租约、优先级派发和终态收敛 |
| Worker | 保留双池、心跳和容量控制，应用执行改为调用新版 Runtime |
| Result Delivery | 保留排队身份、Streaming、Blocking 和终态结果查询 |
| Job 管理 | 保留任务列表、详情、取消、停止、恢复和审计 |

这里需要坚持一个边界：**企业调度层决定“什么时候执行、由谁执行”，Dify 原生 Runtime 决定“应用本身怎么执行”。**

### 4.3 应用执行与 Console 调试

Workflow、Chatflow、Chat、Completion 等应用不再恢复旧 Adapter 体系，而是分别接入 1.17.1 对应的原生执行入口。

| 能力 | 方案 |
| --- | --- |
| Workflow / Chatflow 正式执行 | 托管准入后，由 Worker 调用新版原生执行能力 |
| Chat / Completion | 保留队列、停止和结果查询，业务响应形状保持原生 |
| Agent | 旧 AGENT_CHAT 能力继续迁移；1.17.1 新 AGENT 默认先保留官方路径，是否统一受管单独确认 |
| 草稿调试 | 保留草稿冻结、排队、查询、停止和重连 |
| 单节点 / 迭代 / 循环 | 调度状态接入现有调试面板，节点执行继续使用新版原生能力 |
| Human Input | 原生表单和暂停状态作为事实来源，托管引擎负责恢复代次和调度 |
| 定时触发 | 保留 schedule 纳入统一准入，同一时刻只允许一个调度方负责派发 |

### 4.4 存储与数据安全

存储升级不改变“企业凭据由 KMS 管理”的目标，也不通过改写所有旧对象来追求路径统一。

| 能力 | 升级方案 |
| --- | --- |
| KMS | 保留现有企业 KMS 协议、凭据刷新和错误重试 |
| S3 | 复用 1.17.1 原生 S3 能力，包括新版预签名能力 |
| 文件路径 | 新文件使用统一规则；历史文件按原引用兼容读取 |
| 租户私钥 | 保留历史私钥和路径引用，不因升级重新生成 |
| Redis 缓存 | 只调整需要隔离的企业缓存，不做全库命名空间重构 |

当前已知的“知识库文件删除 S3 对象失败”继续作为升级后的专项验收项，先确定权限、Key 和删除链路，不把它和基线升级混成一个大改造。

### 4.5 管理与可观测

管理端继续提供任务、策略、Worker、健康和审计视图。升级后这些能力只消费新版调度和运行状态，不建立第二套 Runtime 状态。

主要保留：

- 任务列表、详情、筛选和操作；
- Worker 健康、容量和配置；
- Scheduler、队列、依赖健康；
- OTel 指标与审计；
- API、Web、Scheduler、Worker 的独立运行入口。

## 五、数据与兼容迁移

代码能运行只是升级的一部分，历史数据能继续被新版本正确识别才算真正完成升级。

### 5.1 数据库 Migration

官方 1.17.1 和企业旧分支都存在自己的数据库迁移历史。升级时不修改已经执行过的历史 revision，也不把旧库直接标记成新版本。

方案采用：

1. 保留企业历史 migration；
2. 补齐官方 1.17.1 migration；
3. 在完整迁移链都进入新分支后建立合流点；
4. 在数据库副本上分别验证“官方库升级”和“现有企业库升级”；
5. 通过后再用于正式环境。

### 5.2 历史执行数据

已有 Job、generation、workflow run、message 等关联 ID 保持不变。新任务按 1.17.1 数据结构执行，历史任务主要保证可查询、可识别和必要的恢复能力。

Human Input 是这里风险最高的一类数据。旧版暂停上下文和 1.17.1 的恢复上下文结构不同，因此必须先抽取真实暂停记录验证转换；不能转换的记录应阻断对应升级步骤，而不是直接丢弃。

### 5.3 文件与租户私钥

历史 UploadFile Key、S3 对象和租户私钥保持原引用。升级后新写入可以使用统一路径，但旧数据采用兼容读取，不先做全量对象搬迁。

需要重点核对：

| 对象 | 升级要求 |
| --- | --- |
| 历史文件 | 数据库 Key 与 S3 实际对象对应 |
| 新上传文件 | 新版上传、下载、预签名和删除使用同一 Key 规则 |
| 租户私钥 | 旧私钥仍能正常解密，不重新生成 |
| 缓存 | 路径或私钥校正后只失效对应缓存，不清空整个 Redis |

### 5.4 Redis、队列与运行状态

迁移测试阶段 API、Worker、Scheduler 不能直接连接并消费旧环境的业务队列。事件总线、任务队列和定时派发都应使用隔离配置。

正式切换时再让新版组件接管保留的数据和事件链路，并确保旧 Worker、Beat 或 Scheduler 不再同时消费同一类任务。

## 六、部署与版本切换方案

### 6.1 部署关系

新版仍按独立职责运行：

| 组件 | 主要职责 |
| --- | --- |
| Web | Console 与 WebApp |
| API | 登录、管理、应用入口和统一准入 |
| Scheduler | 托管任务排序、派发和终态收敛 |
| Worker | critical / standard 任务执行 |
| PostgreSQL | Dify 原生数据与企业调度数据 |
| Redis | 缓存、队列、事件总线 |
| S3 / KMS | 文件存储与凭据管理 |

Scheduler 和 Worker 是独立运行角色，不隐式挂在 API 进程中。部署平台如果复用同一后端产物，只需要通过不同启动角色区分进程，不需要复制多套代码包。

### 6.2 升级流程

![Dify 基线升级与发布流程](assets/dify-baseline-upgrade/dify-baseline-upgrade-rollout.svg)

发布按“基线准备 → 隔离验证 → 功能联调 → 发布切换 → 观察收敛”执行。

| 阶段 | 主要工作 | 通过条件 |
| --- | --- | --- |
| 基线准备 | 1.17.1 构建、依赖和各进程启动入口可用 | API/Web/Scheduler/Worker 均可独立启动 |
| 隔离迁移验证 | 数据库副本、隔离 Redis/队列、历史文件和暂停数据抽样 | migration 可完成，历史关键数据可读取 |
| 功能联调 | 五个能力域完成端到端验证 | 核心业务链路与旧版目标一致 |
| 发布切换 | 停止旧调度入口，启动新版组件并验证 | 登录、执行、文件、任务管理正常 |
| 观察收敛 | 观察队列、Worker、错误和审计 | 无持续异常后完成升级 |

### 6.3 回滚

回滚不依赖“把新数据删掉再重来”，而是依赖发布前的数据保护和运行组件切换。

- 发布前对数据库和关键对象引用保留可恢复版本；
- 数据结构优先采用兼容新增，破坏性校正必须单独验证；
- 应用异常时先停止新版 Scheduler / Worker，避免继续产生新任务；
- 恢复旧版本 API / Web / Worker / 调度入口；
- 涉及历史数据转换的步骤按对应快照或校正记录恢复。

## 七、测试验收与实施计划

### 7.1 验收范围

| 验收域 | 核心场景 |
| --- | --- |
| 身份与租户 | SkyOA 登录、首次初始化、邀请注册、默认工作空间、owner 权限 |
| 托管执行 | 排队、优先级、Worker 容量、Streaming、Blocking、取消与停止 |
| 应用与调试 | Workflow、Chatflow、Chat、Completion、草稿、单节点、迭代、循环、Human Input |
| 数据兼容 | 旧账号、工作空间、Job、暂停数据、文件和私钥 |
| 存储安全 | KMS 刷新、上传、下载、预签名、删除 |
| 管理与观测 | 任务管理、Worker 健康、Scheduler 健康、OTel、审计 |
| 发布能力 | 新旧版本切换、调度唯一性、异常回滚 |

### 7.2 实施顺序

为了降低一次性迁移范围，按公共底座到业务入口逐步推进。

| 阶段 | 内容 | 当前状态 |
| --- | --- | --- |
| 1 | 平台构建与部署基础 | 代码迁入已完成，实际运行待验证 |
| 2 | 账号、默认工作空间与权限治理 | 迁移方案已完成，待实施 |
| 3 | 数据模型、Policy、Admission、Scheduler、Worker | 迁移方案已完成，待实施 |
| 4 | Workflow / Chatflow / Chat / Completion 与 Console 调试 | 迁移方案已完成，待实施 |
| 5 | KMS/S3、历史文件、私钥、健康与审计 | 迁移方案已完成，待实施 |
| 6 | 数据副本升级、端到端回归和发布切换 | 待前述能力完成后执行 |

### 7.3 实施前需要确认的事项

| 事项 | 原因 |
| --- | --- |
| SkyOA 当前协议与回调约束 | 登录迁移依赖真实协议，不按旧实现猜测 |
| 新 AppMode.AGENT 是否纳入托管执行 | 1.17.1 新 Agent 能力超出旧 AGENT_CHAT 覆盖范围 |
| Redis 事件总线与部署拓扑 | API、Scheduler、Worker 必须使用可达且一致的事件链路 |
| 旧暂停、文件和私钥真实数据 | 需要确认历史格式和对象是否能被新版继续使用 |
| 平台中 Scheduler / Worker 的启动方式 | 决定是否复用 API 后端产物以及最终部署角色 |

升级完成的判断标准不是“所有旧提交都迁入”，而是：**现有企业能力在 1.17.1 上能够稳定运行，历史数据可继续使用，新版原生能力没有被旧实现覆盖，并且部署、监控和回滚链路完整。**
